# 配置参考

## 配置方式

日常设置可在网页「设置」中修改；同时下载数量及暂停、继续操作集中在「最近条目」。设置保存后立即生效并写入数据库。已有数据库中的对应设置优先于环境变量，因此修改 Compose 后，页面中的旧设置仍可能继续生效。

环境变量用于启动配置；修改后执行 `docker compose up -d` 重建容器。仅重启容器不会更新环境变量。首次访问未初始化的实例时会进入设置向导，已通过环境变量配置完整登录账户时直接进入登录页。

## 安装入口与首次设置

- 飞牛图形界面安装：见 [飞牛安装指南](FNOS.md)，使用 [专用 Compose](../deploy/fnos/docker-compose.yml)。它将项目目录下的 `data/` 映射为 `/data`、`media/` 映射为 `/media`，默认媒体库为 `/media`。
- 自定义 NAS 番剧目录：可以直接把专用 Compose 里 `./media:/media` 左侧改成实际绝对路径；也可以下载[离线安装配置页](../deploy/fnos/install.html)后用浏览器打开，填写路径生成完整 Compose。配置页不访问网络；支持复制和下载，端口冲突时可一起调整。生成的新安装配置仍映射 `./data:/data`，旧安装须保留原数据卷。同一页面也随应用分发，容器启动后可在局域网访问 `http://NAS地址:8000/install`（改过端口用新端口）重新生成配置。页面由 `web/src/install/` 源码与现有设计 token 生成，`npm run build` 同时更新离线产物与镜像内 `/install` 页面。
- 飞牛应用包：官方 fnpack 构建 `.fpk`，默认媒体位于共享目录 `auto-anime/media`。宿主 root 生命周期脚本管理容器并按 `TRIM_DATA_ACCESSIBLE_PATHS` 生成具体授权目录挂载，不挂载整卷、宿主应用包、配置或 Docker socket。容器使用非 root 应用用户并移除 capabilities。用户授权后重启应用，再在网页填写路径并检测；目录变更保存前检查写入，失败不保存。非 root 程序副本位于 `/data/runtime/<镜像程序摘要>`，支持自更新；备份整个数据目录包含该目录。详见[飞牛应用包](FNOS_APP.md)。
- 通用 Docker 安装：仓库根目录 `docker-compose.yml` 默认拉取发布镜像，仍保留 `./docker-data:/data`、媒体库留空回退 `/data/downloads`，不会自动迁移已有数据。
- 源码构建：在完整仓库根目录执行 `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`；不要在只有 Compose 文本的飞牛项目中使用构建覆盖文件。

`KEEP_SOURCE_FILES` 默认 `true`，归档后保留下载器源文件继续做种；设为 `false` 或在首次向导/设置页关闭「保留下载器原文件做种」时，归档文件成功提交到数据库后，后台先停止对应下载任务，再删除本次下载器返回的普通源文件，归档副本保留。普通直链无独立做种源文件，不受影响。归档或提交失败不会清理；清理队列持久化，重启后可继续，失败在条目中显示原因并重试。重新开启开关会取消尚未处理的清理，不能恢复已删除的源文件。已经保存的旧条目不会因关闭开关而批量删除。

自动清理支持内置/外部 qBittorrent、Aria2、Transmission。外部下载器须提前配置明确的下载目录/本地映射根目录，源文件超出该目录、与归档重叠、被修改或替换、其他条目共用任务、下载器连接或映射发生变化时保留原文件。只清理返回的源文件，不递归删除目录或控制文件；下载器保留停止的任务记录。归档时仍需同时容纳源文件与副本，关闭做种也要预留归档空间。未配置映射的已有清理记录需手动处理。

首次向导依次设置管理员账户、下载方式、保存目录并确认。它读取当前部署中的下载方式与目录，读取失败时须重试成功后才能保存，避免误用默认值。没有自建下载器时保留内置模式；代理和同步周期为可选项，默认直连与 30 分钟。

保存目录默认沿用部署值，手动修改收在高级选项。未初始化时可点击「检测保存目录」：仅对部署根目录创建、写入、同步并删除临时文件，不接受任意路径，不创建缺失目录，不改变设置。挂载状态区分已映射、未映射、无法确认和非 overlay 环境无需检查；不能确认时不得当作已映射。接口在初始化完成或已配置完整账户后关闭。该检查不能替代真实 NAS 的下载、归档与重建验收，也不会修改 Docker 挂载。

已有部署通过环境变量配置的同步周期会被回填。向导不公开代理地址或凭据，代理输入留空时沿用已有部署代理；没有配置代理时保持直连。需要关闭已有代理时，在安装后的设置页修改。

目录填写的是容器内路径，不能只在网页中填写 NAS 文件夹就认为已经映射。完成后若报告媒体库未映射，页面会保留提示并引导进入设置检查；该检测不等于磁盘、权限与真实 NAS 验收。自动登录失败时使用新账户登录，无需重复安装。正常完成后进入「找番」添加订阅。

网页端口冲突只需改宿主机一侧（如 `18000:8000`），无需改 `PORT` 或健康检查。内置 BT 端口冲突时应同步修改 TCP/UDP 映射两侧与 `QBITTORRENT_BT_PORT`。镜像自带健康检查，精简 Compose 沿用它。

原 Compose 中的外部下载器、代理、账户、Webhook 和更新源等可选环境变量仍受支持，按下表与相应章节自行添加；这一轮只精简示例，并未移除后端配置能力。

## 基础环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DOWNLOAD_MODE` | Docker/Windows 桌面完整包：`builtin`；源码/无下载器单文件版：`direct` | 下载方式，见下表；数据库设置优先 |
| `DOWNLOAD_DIR` | `/data/downloads`（Windows：程序同级 `data\downloads`） | 默认归档目录 |
| `LIBRARY_DIR` | 空 | 媒体库根目录；空时使用 `DOWNLOAD_DIR`，单部番的存储位置优先 |
| `DB_PATH` | `/data/auto-anime.db`（Windows：程序同级 `data\auto-anime.db`） | SQLite 数据库路径 |
| `COVERS_DIR` | 数据库同级的 `covers` | 本地封面缓存目录 |
| `PORT` | `8000` | Web 监听端口；桌面入口仅监听 `127.0.0.1`；Docker 修改时同步调整端口映射和健康检查 |
| `POLL_MINUTES` | `30` | RSS 同步周期，单位分钟，最小 5 |
| `DOWNLOADER_POLL_SECONDS` | `10` | 下载器进度轮询间隔，单位秒，最小 5 |
| `PROXY_URL` | 空 | 默认直连，代理作用范围见下文 |
| `BANGUMI_ENABLED` | `true` | 设为 `false` 关闭自动封面识别 |
| `BANGUMI_API` | `https://api.bgm.tv` | Bangumi API 地址 |
| `WEB_USER` / `WEB_PASSWORD` | 空 | 同时配置才启用登录，也可在向导或设置页配置 |
| `WEBHOOK_URL` | 空 | 接收事件通知的 HTTP(S) 地址 |
| `UPDATE_CHECK` | `1` | 设为 `0` 关闭联网检查新版本（一键更新也随之不可用） |
| `UPDATE_SOURCE` | 空 | 更新源：留空用项目仓库；也可填 `用户名/仓库`、GitHub 仓库地址或自建更新源前缀 |
| `GITHUB_TOKEN` | 空 | 访问 GitHub API 的令牌，用于私有仓库或提高接口限额；不写入日志与接口 |
| `UPDATE_PROXY` | 空 | 仅更新流量使用的代理，留空沿用 `PROXY_URL` |

容器与 Linux 的数据目录默认是 `/data`，与镜像、compose 一致。**Windows 直接运行 Release `.exe` 时**默认用程序同级的 `data\`（数据库、`downloads\`、`covers\` 都在里面）；用 `go run` 调试时该目录在当前工作目录下，避免写进 `go run` 的临时构建目录。程序启动时会打印实际使用的数据库、下载与封面路径。

早期 Windows 版本把数据写在 `<盘根>:\data`（例如 `C:\data`、`E:\data`）：这些数据不会自动搬迁，想继续用就设置 `DB_PATH`（以及需要时的 `DOWNLOAD_DIR`、`COVERS_DIR`）指回原目录。

| `DOWNLOAD_MODE` | 行为 |
| --- | --- |
| `builtin` | 镜像内置 qBittorrent 处理磁力与种子，普通 HTTP(S) 文件由本程序下载 |
| `direct` | 本程序下载 HTTP(S) 文件，磁力与种子条目进入「等待下载器」 |
| `qbittorrent` | 连接外部 qBittorrent（4.4+） |
| `aria2` | 连接外部 Aria2 |
| `transmission` | 连接外部 Transmission |

切换默认下载器影响后续提交，已有任务仍按原下载器跟踪，不会自动转移。内置与外部 qBittorrent 使用独立配置；只要保留内置任务记录，重启后仍会启动内置下载器继续跟踪和做种。

## 内置 qBittorrent

Docker 和 Windows 桌面完整包部署无需填写下载器连接信息。Windows `-desktop.zip` 带有 `qbittorrent/`，桌面入口首次运行默认使用 `builtin`，数据库中已保存的选择优先；仅 `.exe` 和源码运行需提供下载器。程序创建独立配置，不使用电脑上其他客户端的默认配置。Windows 先使用显式 `QBITTORRENT_PATH`，未设置时查找程序同级 `qbittorrent/qbittorrent-nox.exe` 或 `qbittorrent/qbittorrent.exe`，再从 PATH 查找 `qbittorrent-nox`。找不到时仍明确告警并临时降级成 `direct`，已有内置任务不会被改写成外部任务。详见 [Windows 桌面版](WINDOWS.md)。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `QBITTORRENT_DATA_DIR` | 数据库同级的 `qbittorrent/`；镜像为 `/data/qbittorrent` | 配置、凭据、续传数据与下载源文件 |
| `QBITTORRENT_PATH` | Windows 优先程序同级 `qbittorrent/`，否则从 PATH 查找 `qbittorrent-nox` | 可指定完整程序路径，Windows 可指向 `qbittorrent.exe` |
| `EMBEDDED_QBIT_PORT` | `8080` | 仅监听回环地址的 WebUI 端口，Docker 无需映射到宿主机 |
| `QBITTORRENT_BT_PORT` | `6881` | BT / DHT 端口，需与 TCP、UDP 映射一致 |

数据目录中的 `profile/` 保存配置与恢复数据，`downloads/` 保存源文件。连接凭据自动生成并持久化，不包含在设置响应或 JSON 备份中。

Compose 为正常停止留出 45 秒，以便下载器保存会话；关闭时也会取消正在进行的下载器启动，等待子进程退出后再结束服务。

内置下载器运行中意外退出时，主服务保持运行，并自动使用同一私有配置重启子进程。重试间隔依次为 2、4、8、16、32、60 秒，此后最多每 60 秒重试一次；连续运行 5 分钟后重置退避计数。启动尝试最长 30 秒，耗时另计。没有新增配置项，原有环境变量和目录布局保持兼容。首次启动的配置错误（如端口占用或无效凭据）仍会报错，Windows 缺少可执行文件的降级规则保持不变。

每次内置 WebUI 就绪后提供 90 秒会话恢复等待期：暂未加载的旧任务保持原下载器身份、任务 ID 与进度，已暂停任务不会自动继续；任务可见后立即恢复跟踪。超时仍不存在的任务按原有规则报错，不自动重新提交；多个任务具有相同条目标签时拒绝任意绑定。恢复期间 `/api/health` 返回 503，管理页面仍可访问；进程就绪后恢复健康响应。请持久化整个 `QBITTORRENT_DATA_DIR`（默认数据库同级的 `qbittorrent/`，镜像为 `/data/qbittorrent`），仅保留归档媒体不能恢复下载器会话。

### 旧内置 Aria2 升级

镜像已移除内置 Aria2，旧的 `EMBEDDED_ARIA2`、`EMBEDDED_ARIA2_PORT`、`ARIA2_PATH`、`ARIA2_BT_TRACKER` 不再生效。外部 Aria2 接口继续支持。

旧数据库保留原模式，升级后在设置页选择「内置 qBittorrent」。仅对能通过旧私有 `.aria2/session.txt` 与连接配置确认归属、且无法继续运行的未完成任务标记失败，供手动重试；不会将 GID 转成 qBittorrent 任务。

旧配置、下载分片和归档文件保留，不自动迁移或重新下载。重试会向当前下载器提交新任务，不代表已迁移旧分片；独立外部下载器任务不受该升级处理影响。

## 外部下载器

先运行下载器并启用 RPC / WebUI，再在设置页或环境变量中填写连接信息：

| 下载器 | 地址 | 认证 |
| --- | --- | --- |
| qBittorrent | `QBIT_URL`：WebUI 地址 | `QBIT_USER`、`QBIT_PASSWORD` |
| Aria2 | `ARIA2_URL`：如 `http://192.168.1.100:6800/jsonrpc` | `ARIA2_TOKEN`：RPC secret，可选 |
| Transmission | `TRANSMISSION_URL`：如 `http://192.168.1.100:9091/transmission/rpc` | `TRANSMISSION_USER`、`TRANSMISSION_PASSWORD` |

地址必须能从 Auto-Anime 容器访问。容器内的 `127.0.0.1` 指当前容器，连接另一个容器时应使用同一 Docker 网络中的服务名，或 NAS 的局域网地址。

### 下载目录映射

下载器写入文件后，Auto-Anime 必须能读取**同一个 NAS 目录中的同一批文件**才能复制归档：

| 下载器 | 下载器内保存路径 | 同一目录在 Auto-Anime 内的路径 |
| --- | --- | --- |
| qBittorrent | `QBIT_SAVE_PATH` | `QBIT_LOCAL_DIR` |
| Aria2 | `ARIA2_DIR` | `ARIA2_LOCAL_DIR` |
| Transmission | `TRANSMISSION_DOWNLOAD_DIR` | `TRANSMISSION_LOCAL_DIR` |

例如，同一 NAS 目录 `/volume1/downloads` 分别挂载为：

| 容器 | 卷挂载 |
| --- | --- |
| qBittorrent | `/volume1/downloads:/downloads` |
| Auto-Anime | `/volume1/downloads:/source-downloads`（在原 `/data` 挂载之外添加） |

对应配置为：

```yaml
QBIT_SAVE_PATH: /downloads
QBIT_LOCAL_DIR: /source-downloads
```

即 qBittorrent 中的 `/downloads/某集.mp4`，在 Auto-Anime 中是 `/source-downloads/某集.mp4`。两侧路径相同时也必须确保挂载的是同一 NAS 目录。映射错误会导致下载完成后无法归档；修正配置后会再次尝试归档。

归档目标由 `LIBRARY_DIR` / `DOWNLOAD_DIR` 或番剧存储位置决定，与上述源目录映射分开设置。外部下载器的文件、会话和配置需自行持久化、另行备份。

### 番剧文件夹的根目录

归档时总是先在根目录下建立以番剧名命名的文件夹（`<根目录>/<番剧名>/Season XX/…`），不会把集数直接堆在根目录。根目录按以下优先级确定：

1. 添加订阅时在「保存位置」填写的番剧根目录（找番与订阅管理同一个弹窗，只影响该订阅对应的番剧）；
2. 番剧库里为该番单独设置的存储位置（填写的是番剧文件夹本身，不是根目录）；
3. 设置页的「媒体库目录」，即 `LIBRARY_DIR`；
4. `DOWNLOAD_DIR`。

订阅保存位置留空时按 3、4 的顺序回退，并跟随媒体库目录的设置变化；填写后在订阅弹窗中会直接显示实际落点。修改保存位置不会自动搬迁已归档的文件，已有文件需通过条目「纠错」勾选迁移。

### 目录必须映射进容器

上面的根目录（`LIBRARY_DIR`、番剧存储位置、订阅保存位置）都是**容器内路径**。Docker 不会阻止程序写入未映射的绝对路径，但文件会落在容器自己的文件系统里：任务显示「已保存」，NAS 文件管理里却没有，容器重建后还会丢失。

飞牛 fnOS 的实际文件夹路径以文件管理器显示为准，不同存储空间和用户的路径可能不同；不要直接照搬示例中的用户 ID。目录既要映射进容器，也要允许容器进程读取和写入。映射存在不代表权限一定正确；群晖等 NAS 同样需要检查实际路径与权限。

```yaml
volumes:
  - /volume1/docker/auto-anime:/data
  # 飞牛 fnOS：把归档目录按同样路径映射进容器
  - /vol1/1000/番剧:/vol1/1000/番剧
  # 也可以映射成别的名字，此时设置页要填容器内的路径
  - /vol1/1000/番剧:/library
```

保存「媒体库目录」「保存位置」或番剧存储位置时，程序会读取容器的挂载表检查该目录是否落在已映射的目录下；未映射会返回提示（设置页、订阅弹窗、番剧编辑与「存储位置」弹窗都会显示），要求改用已映射的路径或补上 volumes 后重启容器。源码运行（非容器）与 Windows 本机不做此提示。

修改映射后已归档文件不会自动搬迁，需要迁移时用条目「纠错」勾选迁移。

## 版本检查与一键更新

服务启动后会检查一次新版本，之后每 6 小时复查；发现新版本时侧边栏出现提醒，也可在「设置 → 版本更新」手动检查。点「一键更新」后客户端会：下载与当前平台匹配的更新包 → 校验 SHA-256 → 替换程序文件 → 重启服务（同一进程原地重启，容器不会因此重建）。

- **信息来源**：默认读取项目仓库的 GitHub Release（标签、更新说明、附件与 `checksums.txt`）。预发布版本标签的更新说明为空时，会回退读取 Release 页面正文。
- **自建更新源**：把 `UPDATE_SOURCE` 设为前缀（例如 `https://dl.example.com/auto-anime`），服务读取 `<前缀>/latest.json`：
  ```json
  {
    "version": "1.2.0",
    "notes": "更新说明",
    "published_at": "2026-01-01T00:00:00Z",
    "html_url": "https://example.com/releases/1.2.0",
    "assets": {
      "linux-amd64": "https://dl.example.com/auto-anime/auto-anime-1.2.0-linux-amd64",
      "linux-arm64": "https://dl.example.com/auto-anime/auto-anime-1.2.0-linux-arm64",
      "sha256": "更新包的 SHA-256 十六进制值"
    }
  }
  ```
  也可以把 `sha256` 写成 `<更新包地址>.sha256`，内容按 `sha256sum` 的「哈希 文件名」格式。
- **校验**：优先使用更新源提供的 SHA-256；GitHub 源缺少校验文件时只接受直接来自配置仓库地址的下载，自建更新源没有校验值会拒绝更新。

  如果更新源已声明校验文件，但文件请求失败、内容无效或不包含当前平台附件的校验值，会中止更新并允许重试，不降级为无校验安装。
- **更新内容**：Release 正文会显示在弹窗中，纯文本渲染（HTML 已转换为文本），不执行任何页面脚本。
- **忽略版本**：可以「忽略此版本」，仅保存在浏览器本地，出现更高版本时再次提醒。
- **关闭**：`UPDATE_CHECK=0` 后不再联网检查，接口返回 `enabled=false`。
- **私有仓库**：仓库为私有时匿名读取 Release 会返回 404，必须配置带 `repo` 读权限的 `GITHUB_TOKEN`（也可使用 `UPDATE_SOURCE` 指向自建更新源）。仓库公开后该变量可以去掉。
- **仓库改名与 fork**：默认更新源为 `Shizuku11451/auto-anime`；发布工作流会用实际仓库名覆盖它（`-ldflags -X main.defaultUpdateSource=<owner/repo>`），因此 fork 后自行发版不需要改代码，本机构建可用 `-ldflags` 或 `UPDATE_SOURCE` 覆盖。

### Docker 部署的更新行为

| 部署方式 | 一键更新后的结果 |
| --- | --- |
| 发布镜像（`ghcr.io/shizuku11451/auto-anime`），`/app` 可写 | 更新包直接替换容器内可执行文件，并写入 `/data` 暂存副本，重启后即为新版本 |
| 发布镜像，`/app` 只读（默认行为时通常可写，容器以 root 运行） | 更新包写入 `/data` 暂存；下次启动由容器入口与应用引导步骤替换程序文件并自动重启 |
| 本地构建镜像（使用 `docker-compose.build.yml` 覆盖文件） | 可正常更新，但**下次构建镜像会覆盖为新镜像里的旧版本**；把源码更新并重新构建，或把 `/app/auto-anime` 做成挂载卷 |
| 源码运行 | 不提供自动更新（版本为 `dev`），设置页只提示有新版本 |

容器被重建（`docker compose up -d --force-recreate`）时，如果镜像是旧版本，程序文件会回到旧版本，但 `/data` 中保留的暂存更新包会在启动引导阶段重新替换，重启一次即恢复新版本。因此升级镜像与一键更新可以并存：任一路径都能把版本推到最新。

`/app` 不可写时，容器入口会把镜像版本写入 `/data/image-version`，应用据此提示「更新已下载但未能替换程序文件：请用新镜像重建容器」。

### 维护者发布流程

1. 提交并推送源码，打上语义化版本标签：`git tag -a v1.1.0 -m "更新说明" && git push origin v1.1.0`（标签注释会作为 Release 说明；留空则用两次 tag 之间的提交列表）。
2. GitHub Actions 的 `release` 工作流会交叉编译 `linux/amd64`、`linux/arm64`、`windows/amd64` 三个可执行文件，生成 `checksums.txt` 并创建 Release。
3. 同一工作流随后构建并推送 `ghcr.io/shizuku11451/auto-anime:<版本>` 与 `:latest` 镜像；工作流也支持手动触发（`workflow_dispatch`）并填写已存在的 tag。
4. 客户端的更新检查会立即看到该版本。本地构建镜像时可用 `--build-arg VERSION=v1.1.0` 写入版本号，否则镜像内版本为 `dev`。

## 番剧库每周追番

番剧库默认显示横向信息卡片，工具栏可切换「海报墙」，展示方式在当前页面有效。星期导航支持窄屏横向滚动；点击「筛选与日期」展开资源范围、指定日期与放送日说明，收起不清除已选条件。当前结果标题显示星期、日期及数量，可用「清除筛选」恢复全部；排序独立保留。无封面时使用番名占位，简介仍可展开，批量操作栏滚动时保持可见。此布局调整不改变数据、更新日优先级或目录配置。

在番剧详情中选择「编辑番剧」，设置「每周更新日」。默认「自动获取（Bangumi）」：只采用已匹配或手动绑定条目的明确放送星期，不以首播日期或 RSS 发布时间推算。支持中文、日文曜日和英文星期；多日放送、不定期或资料缺失归入「待补充」。卡片区分「Bangumi 放送」与「手动更新」。放送星期按来源标注保留，不将日本深夜时段换算成中国时间；字幕组出片日不同可手动选周一至周日，手动值始终优先，改回自动后跟随资料。

番剧库支持按星期、今天或指定日期查看每周安排，并可叠加名称搜索、资源范围和排序；日期按浏览器本地日历转换为星期，不是该日期的历史到片记录，也不判断开播、完结或停更。切换筛选或排序会清空批量选区。此设置不改变 RSS 同步频率、下载时间或归档目录。

后台沿用 Bangumi 开关及统一出站网络配置。启动和 RSS 同步后检查已有番剧，按已知条目 ID 补全旧资料；自动星期及「暂无明确星期」缓存 7 天，过期后在下一次检查时刷新。网络失败保留原缓存并等待后续重试，不阻塞订阅和下载。关闭 `BANGUMI_ENABLED` 后不联网获取，已有缓存仍可展示。官方站点不可达时可手动设置。

`animes.update_weekday` 保存手动偏好：0 为自动，1–7 为手动周一至周日；上一版本的「未设置」在升级后转为自动，已有手动值保留。创建和更新接口支持同名字段（例如 `{"update_weekday":0}` 恢复自动），省略字段保留原值。列表和详情额外返回只读 `broadcast_weekday`（0 未获取，1–7 来源放送星期），自动缓存记录在 `anime_meta`，绑定变更后不复用旧条目的星期。JSON 备份只保存手动偏好，自动资料恢复后重新获取；旧备份缺少此字段时按自动处理。合并保留目标番剧设置。无新增环境变量或目录配置。

## 任务列表、认证与故障恢复

- 最近条目：每页最多 100 条，搜索与状态筛选在数据库中先执行，再分页；输入停止 350 毫秒后搜索，回车立即提交，「清除筛选」同时清除关键词与状态条件。列表上下均可翻页，第二页起可回到首页；本页条数与全库状态数量分开显示。可见页面每 5 秒自动更新，另有手动刷新入口。
- 条目详情默认收起，展开后显示原始标题、发布时间、下载方式与已保存文件的归档位置，并提供存储位置、纠错及移除记录操作。下载进度、速度和失败原因在列表中直接显示；暂停后的直链下载会提示继续时从头下载。
- 批量管理工具栏在滚动时保持可见，仅对本页选中且符合操作状态的条目生效；修改搜索、切换状态或翻页会清空选区，操作及移除确认期间锁定选区。部分失败仍保留选中供重试，移除记录始终保留已保存文件。以上界面行为不增加环境变量，不迁移目录，也不改变已有下载器与任务身份。
- API 兼容：`GET /api/items` 仍返回最多 100 条的数组；加 `page=1` 返回 `{items,next_before}`。下一页传 `before=next_before`（0 表示没有下一页），`group` 使用界面状态组名称；原有 `q`、`status` 精确状态参数继续可用。
- 手动同步仅接受 `POST /api/sync/<订阅ID>`，请求取消会停止后续获取和条目处理；已经成功写入的条目会保留，不重复下载。
- 网页登录与 Basic Auth 共用来源 IP 的失败计数：连续 5 次失败锁定 15 分钟，锁定时返回 HTTP 429。反向代理部署时计数依据直接连接来源，同一代理后的用户会共享额度。
- 新密码使用 bcrypt（先 SHA-256 预哈希以支持长密码）；旧 v1 哈希在成功登录时升级，不撤销已有会话。更换密码仍会撤销会话。升级后旧程序无法验证 v2 哈希，回退程序前应恢复对应的数据库备份。
- 设置保存仍按事务处理，运行中的请求读取配置快照；代理切换不修改正在请求中的 HTTP Client。
- 归档提交记录保存在同一 SQLite 数据库的 `archive_commits` 表中，不增加环境变量。文件发布前写入记录，文件发布后事务更新“已保存”并清除记录；失败时后台轮询及启动恢复优先提交原文件，不重复复制，单文件与未识别单集编号的多文件合集目录均支持恢复，并校验提交标记。暂停任务不会被恢复过程自动继续，用户纠正或新任务不会被旧记录覆盖。
- 若归档媒体存在但配套提交标记不完整，系统保留原文件并报告检查提示；这不代表已保存成功，需要检查存储与文件完整性。完整数据库备份包含提交记录，网页 JSON 订阅备份不包含它们。

开发检查由 `.github/workflows/checks.yml` 在分支推送和 PR 时执行，发布也依赖该检查；包含前后端测试、构建、Go 静态检查和配置并发回归的 race 检测。手动发布必须指定已有的 `v*` 标签，二进制、前端与镜像均从该标签提交构建。
